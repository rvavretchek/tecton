# Product Brief: Tecton

## Sumário Executivo

Tecton é um framework React.js + Node.js de uso geral, **modular orientado a microsserviços por domínio**. Ele não serve para começar um sistema do zero — a estratégia recomendada continua sendo monólito primeiro — mas para quem já tem maturidade de domínio e precisa migrar: um monólito maduro sofrendo com custo/escalabilidade, ou um legado maduro sem documentação cujo PO conhece bem o negócio. O núcleo é um manifest declarativo de domínio (contratos, eventos, dependências) que gera interoperabilidade sem *plumbing* manual, e que serve tanto ao desenvolvedor humano quanto a um agente de IA como contrato legível do que pode ser alterado com segurança. O framework nasce com domínios prontos que qualquer sistema sério precisa reinventar — Tenant, Usuário/Grupo, e (como extensão futura) Custódia de chave — todos declarados como classes de objeto num core único de diretório hierárquico com gestão *drag-and-drop*, inspirado no NDS/NetWare.

## O Problema

Equipes que constroem greenfield em microsserviços geralmente pagam um preço alto sem necessidade — a arquitetura certa para um domínio ainda não comprovado é o monólito. O problema real aparece depois: um sistema monolítico que deu certo, cresceu, e agora custa caro pra escalar, ou tem partes que precisam evoluir e ser implantadas em ritmos diferentes. Nesse ponto, quem migra reinventa do zero: interoperabilidade entre serviços, contratos formais de dados/eventos, e funcionalidades transversais que todo sistema multi-tenant sério acaba precisando (gestão de inquilinos, de usuários/grupos, de custódia segura de dados sensíveis para conformidade). Além disso, bases de código distribuídas em múltiplos serviços são particularmente difíceis de editar com segurança por agentes de IA quando não existe um contrato explícito e legível por máquina delimitando o que cada serviço expõe e depende.

## A Solução

Tecton fornece:

1. **Manifest declarativo de domínio** (`tecton.yaml`, um por domínio, `manifestVersion` próprio) — declara `objectClass` **opcional** (containment + ACL herdável, só para domínios que participam do core de diretório — Tenant, Usuário/Grupo, Custodiante; domínios de negócio comuns como Catálogo ou Relatórios não têm), `actions` (com `sensitive.quorum`/`description` obrigatória quando aciona o Custodiante, e `approval` — primitivo nativo de aprovação simples reaproveitando o ACL/árvore, para fluxos de negócio como "gerente aprova"), e `events` publicados/consumidos — inclusive entre domínios (um domínio sem dados próprios, como Relatórios, consome eventos de outros e mantém um modelo de leitura local, em vez de acessar banco alheio). O framework gera os conectores de mensageria e exporta OpenAPI/AsyncAPI automaticamente a partir disso — nunca o contrário. Ver exemplos de referência em `docs/examples/tenant-domain-manifest-v0.yaml` e `docs/examples/leave-domain-manifest-v0.yaml`. É também o artefato que um agente de IA lê antes de alterar um serviço.
2. **Core genérico de objeto/diretório hierárquico** — schema declarado, gestão por *drag-and-drop*, persistência em Closure Table (via Prisma: PostgreSQL, MySQL, MS-SQL), controle de acesso por **herança aditiva simples** (permissão flui pros descendentes por padrão; bloqueio/override por nó fica como extensão futura explícita — descartado do MVP por risco de opacidade, contrário ao objetivo de legibilidade por agente de IA), com schema desenhado em relações estilo ReBAC para permitir troca por um motor de autorização dedicado (ex.: OpenFGA) no roadmap sem reforma. Qualquer domínio embutido ou de terceiros é, no fundo, uma classe de objeto declarada nesse core.
3. **Domínios embutidos prontos**: Gerenciamento de Tenants, Gerenciamento de Usuários e Grupos (MVP entrega a árvore como navegação/leitura, sem *drag-and-drop* — reaproveitado do Aether, que constrói essa UI primeiro, num release posterior; ver Escopo), e Gerenciamento de Custodiantes — este último cuida de custódia de chave de criptografia por limiar (estilo Shamir), com aprovação x/n criptograficamente forçada para operações sensíveis (dumps, relatórios grandes/sensíveis), voltado a LGPD/GDPR/HIPAA.
4. **CLI** (`tecton-admin`, único binário, sem estrutura de dois níveis à la Django) com vocabulário compartilhado com o Aether (`new`, `generate <tipo> <nome...>`, `dev`, `migrate`), `generate domain` aceitando múltiplos nomes de uma vez (variádico) ou um arquivo de planejamento (`--from`) para quem já chega com os domínios definidos; `test:contracts` roda o Contract Testing derivado do manifest; `extract` (migração assistida) e `mcp:serve` reservados no `--help` como roadmap. Persistência via **Prisma** (mesmo ORM do Aether — Postgres/MySQL/MS-SQL; Oracle fora do MVP).
5. **Suporte a dois caminhos de adoção**: migração assistida a partir de um monólito documentado (Caso 1), e scaffolding opinativo que remove decisões arquiteturais do desenvolvedor quando o domínio já é bem conhecido pelo PO mas não documentado (Caso 2).
6. **Formato de resposta de API padronizado, adotando specs existentes**: sucesso como payload puro (sem envelope, exatamente o `output` do manifest) com correlação via header `traceparent` (W3C Trace Context, mesmo padrão já usado pelo OpenTelemetry); erro como **RFC 9457 Problem Details** (`type`/`title`/`status`/`detail`/`instance`), com a extensão de comunidade `invalid-params` para erro de validação por campo; estado "pendente de aprovação" (ação `sensitive`/quórum do Custodiante) como `202 Accepted` dedicado, nunca dentro do formato de erro.
7. **Experiência de desenvolvimento**: **Fastify** como servidor embutido (validação de schema nativa, mais rápido que Express em benchmark, contra menor ecossistema/modelo de encapsulamento — trade-off explícito e assumido, mitigado porque o dev raramente escreve Fastify na mão, o manifest gera a rota); OpenAPI via `@fastify/swagger` (gerado da mesma rota, não escrito à mão); Dev Services via `docker-compose.dev.yml` (Valkey + banco); Live Reload via `tsx watch` orquestrado por `turbo run dev`.

## O Que Torna Isto Diferente

Pesquisa comparativa (2026-08-11) contra os três concorrentes mais próximos no ecossistema Node/TS:

- **Moleculer.js** — schema de serviço declarativo (nome, ações, eventos), `ServiceBroker` embutido, múltiplos transportes (NATS, Redis, MQTT, TCP), tolerância a falha embutida (circuit breaker, retry, timeout, bulkhead). É o concorrente mais próximo do núcleo manifest+broker do Tecton — sobreposição real, não só parecida.
- **Dapr** — *building blocks* como APIs padronizadas (invocação de serviço, estado, pub/sub etc.) via sidecar, agnóstico de linguagem. Mecanismo diferente (sidecar vs. framework in-process), mesma categoria de problema.
- **NestJS microservices module** — transporte orientado a mensagem (TCP, Redis, NATS, MQTT, gRPC, Kafka, RabbitMQ) sobre a base do Nest. Sem ferramental de migração dedicado: a orientação de 2026 é extração manual gradual (padrão *strangler fig*), não algo que o framework automatize.

**Achado que confirma a tese, não só a sustenta**: nenhum dos três oferece (1) ferramental de migração assistida a partir de um monólito real, (2) um core genérico de objeto/diretório hierárquico com drag-and-drop (esse território pertence a produtos de diretório corporativo — NDS, Active Directory — não a frameworks JS de microsserviços), ou (3) um domínio de custódia de chave por limiar embutido. A diferenciação do Tecton está exatamente nesses três pontos, mais tratar um **agente de IA como consumidor de primeira classe** do manifest de domínio — nenhum dos três concorrentes se posiciona nesse eixo (ausência observada, não testada de forma exaustiva).

**Achado que valida a premissa do projeto**: a pesquisa sobre NestJS também trouxe um sinal independente forte — o debate de 2026 em torno de monólito-vs-microsserviços amadureceu a ponto de "um número surpreendente de times reverter para monólitos modulares", com "modular monolith como etapa intermediária útil antes de microsserviços". Isso é evidência externa, não só opinião da Mary, para a premissa "Monolith First" da Constitution §2.

*Fontes*: [Moleculer Core Concepts](https://moleculer.services/docs/0.14/concepts.html), [Moleculer Service Broker](https://moleculer.services/docs/0.14/broker.html), [Dapr Overview](https://docs.dapr.io/overview/), [Dapr sidecar architecture](https://manueljavier.com/posts/dapr-sidecar-architecture), [NestJS Microservices Guide 2026 — Encore](https://encore.dev/articles/nestjs-microservices-guide), [Monolith to Microservices: A Strategic Migration Approach with NestJS](https://medium.com/@asierr/from-monolith-to-microservices-a-strategic-migration-approach-with-nestjs-e9e9d655e42c).

*Limite honesto*: pesquisa por busca web, não uma auditoria exaustiva de cada ferramenta — trata ausência observada como sinal forte, não como prova definitiva de que nenhuma delas resolve isso de algum jeito não indexado pela busca.

## A Quem Isso Serve

**Primário**: desenvolvedores solo ou pequenas equipes com domínio já maduro — (Caso 1) donos de um monólito com dor real de escalabilidade, dispostos a desenhar uma estratégia de migração; ou (Caso 2) desenvolvedores construindo para um PO que conhece profundamente um domínio legado não documentado, e que querem que o framework remova decisões de arquitetura/tecnologia para poderem focar em especificar bem os limites de domínio.

**Secundário (motivação pessoal do autor)**: o próprio criador, usando o Tecton como peça de portfólio pública e prática deliberada de desenvolvimento orientado a domínio/microsserviços — qualquer desfecho (aprendizado, adoção real, comunidade formada) já é considerado sucesso.

## Escopo

**Dentro (trilha MVP)**: núcleo de manifest declarativo/interoperabilidade; core genérico de objeto/diretório com *drag-and-drop*; domínio Tenant; domínio Usuário/Grupo; encaixe de extensão declarativo para provedores plugáveis (a começar por um `KeyCustodyProvider` agnóstico de fornecedor) — apenas a interface, sem implementação pesada. Primitivo nativo `approval` (aprovação simples de negócio, reaproveita ACL/árvore) — sempre disponível, sem motor externo. `tecton-admin extract`: scaffold de domínio + fachada de roteamento no gateway (strangler fig) + script de export/import único de dados, para migração assistida do Caso 1 (corte único, com janela de manutenção; sincronização contínua/CDC fica roadmap). Autenticação centralizada via `AuthProvider` (Argon2id + Pepper, JWT + Refresh confinado ao serviço de Auth, *claims* propagadas via gateway) com revogação `TokenRevocationStore` **Valkey-backed real** (não seam — Valkey já é dependência padrão do transporte assíncrono, custo marginal baixo). **Zero Trust na comunicação interna** (Constitution §9): todo serviço verifica a assinatura do token ele mesmo (nunca confia em header pré-decodificado por "estar na rede interna"); toda chamada serviço-a-serviço carrega credencial verificável, inclusive tráfego leste-oeste. Também dentro do MVP, após a triagem completa do `Tecton.md` (ver addendum para a tabela item a item): **API Gateway fino** (roteamento gerado do manifest, validação de token, rate limiting via Valkey, propagação de trace — explicitamente proibido de fazer circuit breaker, retry automático em mutação, cache de resposta, transformação de payload, agregação de múltiplos serviços ou autorização por regra de negócio, com `tecton-admin lint:gateway` — script portável de CI + template GitHub Actions — barrando dependência fora da allowlist do pacote), **service discovery estático** via variável de ambiente gerada por domínio (Consul/Eureka descartados — obsoletos frente a DNS nativo de Kubernetes no roadmap), **transporte assíncrono** via Valkey Streams com envelope **CloudEvents** (at-least-once, exige handlers idempotentes por design), `ConfigProvider` com validação tipada no startup (candidato de roadmap **OpenBAO**, não Vault, mesma lógica do `KeyCustodyProvider`; AWS Parameter Store/Secrets Manager como alternativa opcional), autenticação centralizada (libs maduras), DI/IoC leve, regra de persistência por serviço, observabilidade distribuída (OpenTelemetry), contract testing e geração de OpenAPI/AsyncAPI (ambos derivados de graça do manifest), health checks, TypeScript full-stack, e Turborepo/Nx no *scaffold* gerado para apps construídas com o Tecton (não no repositório do próprio framework).

**Também dentro do MVP (Bloco B — resiliência/operação)**: `ServiceClient` gerado a partir de `dependencies` do manifest, com retry+timeout (retry só em ação idempotente ou mutação com `Idempotency-Key` explícito, nunca retry cego); health checks em `/health`, `/ready`, `/live` (convenção de probes do Kubernetes) gerados automaticamente por serviço; Dockerfile por domínio (deploy independente, seam).

**Também dentro do MVP (Bloco C — padrões de dados)**: CQRS leve nativo via `events.consumes` + modelo de leitura local (sem feature nova); Contract Testing gerado dos dois lados do manifest (publisher: `output` vs. resposta real; consumer: schema esperado vs. `events.publishes` de quem publica — mais simples que Pact porque o manifest já é o contrato compartilhado, sem arquivo separado a sincronizar); evolução de API **aditiva por padrão** (nunca remove/renomeia campo existente, só adiciona opcional) — absorve o item "Independent Model Evolution", que era o mesmo problema com outro nome.

**Também dentro do MVP (Bloco D — developer experience)**: AsyncAPI gerado do `events` do manifest (via transform + `@asyncapi/parser` para validação); Testcontainers para isolamento de `test:contracts`/CI (contexto diferente do Dev Services, que é conveniência de loop de dev); formulário de edição de objeto gerado via `@rjsf/core` (projeto react-jsonschema-form sob o namespace ativo `@rjsf`) a partir de `objectClass.attributes`.

**Fora por ora / Roadmap**: árvore *drag-and-drop* ciente de ACL — **correção de 2026-08-15**: MVP entrega só navegação/leitura da árvore; a UI *drag-and-drop* é roadmap com plano concreto de reaproveitar a implementação do Aether (produto mais leve, sai primeiro) em vez de duplicar trabalho — não é mais "trabalho genuíno do zero", é herança planejada entre os dois projetos; Compilação AOT; Continuous Testing; Event Sourcing completo por domínio (`persistence: eventSourced: true`, ferramental de replay/snapshot) — reservado para domínios com exigência real de reconstrução no tempo/trilha de auditoria imutável (ex.: Custodiante já tem esse requisito por natureza); versionamento explícito de API (`v2`, nova action) só quando a mudança quebra compatibilidade, com detector automático de quebra comparando manifests (mesma família do `lint:gateway`); circuit breaker/bulkhead no `ServiceClient` (candidato de biblioteca: `opossum`); pipeline de CI/CD com release independente por serviço; `tecton-admin generate k8s` (Deployment/Service/NetworkPolicy por domínio, a partir do que o manifest já declara); `tecton-admin generate ci <plataforma>` para além do template GitHub Actions do MVP (GitLab CI, CircleCI, Jenkins etc. — sob demanda, não dia 1); implementação real do domínio Custodiante (integração com OpenBAO/Vault/HSM, quórum criptograficamente forçado, log de auditoria encadeado/assinado); sincronização contínua/CDC para migração sem downtime (Caso 1); pesquisa formal de diferenciação competitiva vs. Moleculer/Dapr/NestJS microservices (feita em nível inicial, ver acima); resiliência avançada (circuit breaker/bulkhead), deploy independente completo, CQRS/Event Sourcing, Kubernetes Native (agora incluindo NetworkPolicies como parte da maturidade Zero Trust — contenção de raio de explosão na camada de rede) e mTLS/service mesh (Istio/Linkerd ou SPIFFE/SPIRE) para maturidade avançada de Zero Trust (NIST SP 800-207) além da verificação por serviço já MVP. **`WorkflowEngineProvider`** (unifica o antigo encaixe de coordenador de Saga com workflow de negócio complexo — paralelismo, compensação, espera durável; via integração com motor consagrado, candidato inicial Temporal, decisão de motor em aberto) — interface prevista, implementação roadmap. **MCP por domínio: 100% roadmap, zero escopo de MVP dedicado** — o manifest já contém tudo que a geração vai precisar (não é preciso preparar nada a mais agora); quando implementado: read-only por padrão, mutação via opt-in explícito, ações `sensitive` continuam exigindo quórum do Custodiante mesmo via agente, hospedagem como serviço dedicado (voto provisório do autor). **UI Generation from Contracts** (item promovido de rodapé do `Tecton.md`) se divide, como detalhado acima: formulário via `@rjsf/core` é MVP; a árvore *drag-and-drop* ciente de ACL é trabalho genuíno, roadmap. **Rejeitados**: Single-File Applications (contradiz a identidade modular do framework) e Chaos Engineering (prematuro para este estágio).

Tecton compartilha autor e várias decisões de subsistema (por convergência independente) com um projeto irmão monolítico — ver `docs/aether-tecton-compatibility.md`, único lugar deste repositório que trata do assunto. Compartilhamento de código real entre os dois só ocorre quando não gerar impacto arquitetural e trouxer ganho real (redução de esforço/padronização) — decisão concreta fica para quando houver código suficiente dos dois lados para avaliar.

**Explicitamente fora deste projeto**: construir uma aplicação de demonstração fictícia (ingressos, e-commerce, billing) só para provar a arquitetura — descartado deliberadamente; os próprios domínios embutidos cumprem esse papel de prova.
